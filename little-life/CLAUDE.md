# LITTLE LIFE

현실의 작은 행동을 퀘스트·탐험·수집·성장으로 바꾸는 현대 생활 판타지 RPG.
Vite + React + TypeScript + Tailwind. 폰에서 쓰는 PWA.

> 재미있는 세계가 궁금해서 현실에서 움직인다.
> 현실에서 움직였기 때문에 세계가 조금 더 열린다.

생산성을 강요하는 앱이 아니다. **현실 행동은 이야기의 입장권이 아니라,
이 세계와 함께 살아온 기록이다.**

자세한 방향은 `docs/direction/` 여덟 장에 있다. 새 기능을 설계하기 전에 읽는다.

## 절대 규칙

사용자가 직접 말하지 않는 한 이 선을 넘지 않는다.

### 사람을 대하는 방식

- **꾸중하지 않는다.** 연속 출석, 놓친 날 경고, 시무룩한 캐릭터를 만들지 않는다.
- **미접속을 벌주지 않는다.** 하루 안 왔다고 친밀도가 줄거나 관계가 끝나지 않는다.
- **오늘 안 하면 손해인 구조를 만들지 않는다.** 매일 해야 하는 일과 하루 제한은
  그 자체로 숙제다. 실패·패배·랜덤 실패도 만들지 않는다.
- 중요한 장면은 시간을 놓쳤다고 영영 사라지지 않는다.

### 구조

- **파생 가능한 상태를 저장하지 않는다.** 셀 수 있으면 세고, boolean 을 굳히지 않는다.
  (예: 문이 열렸는지는 `doorOpen` 이 아니라 밟은 걸음 목록에서 계산한다.)
- **새 시스템 전에 기존 코드를 먼저 조사한다.** 조사 결과를
  ① 그대로 재사용 ② 작은 확장 ③ 정말 신규 로 나눠 보고한 뒤 구현한다. ③ 은 되도록 없어야 한다.
- **새 화폐 · 새 에너지를 만들지 않는다.** 있는 코인과 `adventureEnergy` 를 쓴다.
  에너지가 0이어도 화면 열람 · 기록 확인 · 이미 연 곳 이동은 된다.
- **보상 계산을 복제하지 않는다.** 한 군데서만 한다.
- 한 업데이트의 범위를 넘지 않는다. 다음 것은 Hook 만 남긴다 —
  **Hook 은 떡밥이지 구현이 아니다.**
- 기존 저장을 깨지 않는다. 신규 필드는 기본값, 모르는 id 는 sanitize 로 걸러낸다.
  중복 지급이 안 생기게 flag 를 챙긴다.

### 그림

- **없는 에셋을 지어내지 않는다.** 코드로 그리지 말고 무엇이 없는지 적어서 요청한다.
  이모지 한 글자가 이 프로젝트의 placeholder 다 (`npm run assets:audit` 이 센다).
- **그림이 일부만 왔다고 나머지를 화면에서 빼지 않는다.** 사람 얼굴은
  지금 스물넷 다 있지만, 없는 사람은 이모지로 떨어지는 길을 그대로 둔다 —
  사람이 늘면 그림보다 먼저 도시에 서는 때가 온다. 부르는 쪽(`NpcFace`)이
  둘을 구분하지 않아서 화면마다 조건문이 안 생긴다.
- **색 필터로 기존 그림을 다른 물건처럼 쓰지 않는다.** hue-rotate 금지.
- 캐릭터 옷은 **완성된 한 장 = 한 벌**. 상의/하의/머리로 나누는 레이어 방식은
  한 번 만들어봤다가 접었다. 되살리지 않는다.
- 금지: 네온 · 다크판타지 RPG UI · 두꺼운 금테 · 진한 그림자 · 과한 입자.
  파스텔, 낮은 대비, 둥근 실루엣, 은은한 수채 질감.
- 희귀함은 반짝이 입자가 아니라 색조와 재질로 말한다.

### 이름

- **확정명이 없으면 짓지 않는다.** 리포 · 시트 파일명 · 문서 · git 기록을 끝까지 찾고,
  그래도 없으면 자리표(`PACK7_SKIN_73`)로 두고 `nameMissing` 을 켠다.
  id 에도 뜻을 담지 않는다 — 나중에 진짜 이름이 오면 파일명만 딴소리를 하게 된다.
  (실제로 두 번 그랬다.)
- 이름이 오면 **id · 이름 · 그림 파일을 한 번에 같이** 정한다.
- **사람 이름이 바뀌어도 npc id 는 안 바꾼다.** 저장이 친밀도 · 읽은 이야기 ·
  비밀 장소 · 던전 입구를 전부 id 로 붙잡고 있다. 처음 여섯은 이렇게 붙어 있다 —
  `MINA`=윤하루(카페) · `HARU`=윤태오(공원·러닝) · `LULU`=오미래(공방) ·
  `JUNE`=서이안(빈티지숍) · `RIO`=한도윤(클라이밍장) · `NOA`=차세라(밤거리·BAR).
  이야기 장 id(`HARU_5` = 오래된 열쇠)와 가게 id(`MINA_CAFE`, `JUNE_CLOSET`,
  `JUNE_VINTAGE`)도 같은 이유로 옛 이름을 그대로 쓴다. 나중에 들어온
  열여덟은 이름이 확정된 뒤에 만들어서 id 가 곧 이름이다(`EUNCHAE`, `SIWOO` …).
  성격과 관계는 `docs/direction/06_NPC_CHARACTER_BIBLE.md` 가 기준이다.

## 이 리포에서 일하는 법

작업 디렉터리는 `little-life/` 다. 리포 루트에서 `npm` 을 돌리면 안 된다.

```bash
npm run typecheck     # tsc -b --force  ← 진짜 타입 검사
npx vitest run        # 단위 테스트 (little-life/ 안에서)
npm run assets:audit  # 빠진 그림 · 이름 · 캔버스 점검
npm run assets:skins  # 시트에서 캐릭터 옷 잘라내기
npm run assets:npcs   # 시트에서 사람 얼굴 잘라내기
npm run assets:thumbs # 목록용 작은 그림
npm run build
```

**`npx tsc --noEmit` 은 조용히 통과한다. 믿지 마라.** `npm run typecheck` 만 진짜다.

### 브라우저 검수

바뀐 화면은 실제로 열어본다. 미리보기는 이 순서로 띄운다 —
번들 해시를 확인하지 않으면 예전 걸 보고 통과시킨다.

```bash
npm run build && rm -rf /tmp/dist-noenv && cp -r dist /tmp/dist-noenv
pkill -f "[b]in/serve"; (cd /tmp/dist-noenv && npx serve -s -l 4321 &)
curl -s localhost:4321 | grep -o 'index-[A-Za-z0-9_-]*\.js'   # dist/index.html 과 같은지
```

Chromium 은 `/opt/pw-browsers/chromium`, `serviceWorkers: 'block'`, 390×844.

### 캐릭터 그림

`/assets/characters/<skinId>.webp` — 경로를 아는 곳은 `skinArt()` 하나뿐이다.
120장이 전부 **같은 캔버스(433 × 508) · 같은 발 기준선**에 서 있다.
`extract-skins.py` 가 판에 들어온 조각 전부에서 캔버스를 계산하므로
**새 시트만 따로 돌리면 안 된다. 늘 전체를 한 번에 돌린다.**

크기는 감싸는 상자가 정한다. `CharacterSkinRenderer` 에 `className` 으로
`h-[..]` 를 또 주면 안의 `h-full` 과 싸워서 어느 쪽이 이길지 모른다.

## 지금까지 온 길

UPDATE A 정원 → B 부엌 → C 작업실 → D 채석장 → E 오래된 열쇠와 첫 던전
→ F 생명체 넷과 안쪽의 큰 방 → F.5 의상실과 옷 120벌
→ G 리빙시티 1 — 여섯 사람의 하루 동선과 영업시간
→ G.5 그림 지도 — 도시 한 장 위에 지금 상태를 얹는다
→ H 맥락 대사 — 어디서 언제 만났느냐에 따라 조금 다르게 말한다
→ H.5 얼굴 — 이모지 자리에 스물넷의 그림이 들어왔다
→ I 선물과 취향 — 가지고 있던 걸 하나 건네본다
→ J 리빙신 — 내가 안 볼 때도 도시가 굴러가고 있었다
→ **K 개인 이야기 시범 — 정시우 「뜨거운 철판이 식은 뒤에도」** (여기까지 완료)

다음은 **코어 1.0 점검**. 두 번째 개인 이야기는 그전에 만들지 않는다 —
시범이 재미없으면 스물넷에게 펼칠 이유가 없고, 재미있어도 점검이 먼저다.

**세 가지가 서로 다른 것이다.** 여기를 섞으면 전부 망가진다.

| | 무엇 | 몇 번 | 어디에 |
| --- | --- | --- | --- |
| 생활 대사 | 그 사람을 눌러서 듣는 말 | 몇 번이고 | `city/living-lines.ts` |
| **리빙신** | 그 자리에 있던 **두 사람 사이**의 일 | **한 번** | `city/scenes.ts` |
| 이야기 장 | 그 사람이 **나에게** 하는 말 | 한 번 · 관계가 진전 | `discovery/stories.ts` |
| **개인 이야기** | 그 사람 옆에 **다른 사람이 같이 서 있는** 장 | 한 번 · 보상 없음 | `discovery/stories.ts` (`scene`) |

**개인 이야기는 이야기 장 틀을 그대로 쓴다 (K).** 새 엔진을 만들지 않았다 —
`StoryChapterDef` 에 `scene?: LivingSceneLine[]` 한 줄만 더했고, 그게 있으면
화면이 지문과 이름을 그린다. 줄 모양은 리빙신(J) 것을 재사용한다.
초반 열다섯 장은 손대지 않았다 (`scene` 없이 `lines` 그대로).

**시우 여섯 장은 보상이 0이다.** 앞 열다섯은 친밀도 3~5를 주는데 여기서
같이 주면 "이야기를 읽으면 친밀도가 오른다" 가 되고, 그때부터 읽는 게
아니라 여는 게 목적이 된다. 조건도 친밀도(6·14·22·28·34·40)와 동네
평판 둘뿐이다 — **선물도 리빙신도 이야기를 여는 열쇠가 아니다.**

**과거는 마지막 장에서만 나온다.** 1~5장에 밴드·보컬·무대 같은 말이
하나도 없는 걸 테스트가 지킨다. 5장의 재킷은 힌트고, 이안은 알고 있어도
대신 설명해주지 않는다. 다 읽고 나면 시우 생활 대사 두 줄이 열린다
(`NpcDialogue.afterChapterId`) — 스물넷 중 시우에게만 있다.

리빙신(J)에서는 아무 일도 안 일어난다. 코인도 경험치도 친밀도도 아이템도
없고 선택지도 실패도 없다. **내가 보지 않은 시간에도 이 도시가 굴러가고
있었다는 증거** 하나가 남는 게 전부다. 그래서 `3/8` 같은 진행도도,
지도의 `!` 표시도, 알림도 만들지 않았다 — 그게 붙는 순간 이건 우연히
마주친 게 아니라 오늘 안에 다 찾아야 할 목록이 된다.

**장면을 보여주려고 사람을 옮기지 않는다.** 등장하는 사람이 지금 정말
그 동네에 있어야 뜬다 (`npcAreaNow`). 동선이 확률이라 어떤 날은 조건이
안 맞고 그건 정상이다 — 못 본 장면은 사라지지 않고 조건이 맞는 다음
날 그대로 거기 있다. 여덟 장면 다 동선을 하나도 안 고치고 성립한다
(제일 드문 게 하루×태오 아침 13%, 제일 잦은 게 미래×이안 낮 83%).

**닫으면 아직 안 본 것이다.** "다 봤어" 를 눌러야 적힌다 — 실수로 닫았는데
영영 못 보게 되면 그건 벌이다. 한 자리에 후보가 둘이어도 **하나만**
돌려준다 (`sceneHere`). 둘을 연달아 틀면 우연이 아니라 상영회다.

**생활 대사는 이야기가 아니다.** `city/living-lines.ts` 의 208줄은 몇 번이고
다시 나와도 되는 말이고, 거기서 정체 · 과거 · 관계의 핵심을 밝히지 않는다 —
그건 이야기 장(StoryChapter)이 할 일이고, 생활 대사가 먼저 말해버리면
나중에 그 장을 읽을 때 이미 아는 얘기가 된다. 그래서 이안의 정체도,
시우의 옛 밴드도, 세라와 재희 사이도 생활 대사에는 없다.
지호가 시우의 과거를 모르는 것처럼 **그 사람이 모르는 남의 사정도 안 적는다.**

**F.6 작은 옷장은 사용자가 하기로 정해서 만들었다.** F.5 때 자리만 있던
GACHA 48벌(묶음 넷)을 실제로 뽑을 수 있게 했다. 방향 문서 `02` 의 F 절은
아직 가챠를 "만들지 않을 것" 에 적어두고 있는데, 그 결정을 뒤집은 건
사용자다 — 문서를 고칠지는 사용자가 정한다.

작은 옷장의 규칙은 확률표가 아니라 **수집 상자**다:
**이미 가진 옷은 안 나온다** (남은 것 중에서만 고른다). 그래서 조각도
천장도 중복 보상도 없다 — 그것들은 전부 "중복이 나온다" 는 문제를 덮는
장치다. 한 묶음 열두 벌이면 끝나고, 다 본 칸은 버튼이 사라진다.
한 번 320 코인 (보통 퀘스트 넷). 의상실에서 원하는 옷을 바로 사는 480
보다 반드시 싸야 한다 — 무엇이 나올지 모르는 쪽이 더 비싸면 아무도 안 연다.

저장 판올림은 **v19**. G · G.5 · H · H.5 는 저장을 하나도 안 늘렸다 —
누가 어디 있는지도 가게가 열렸는지도 전부 날짜·시각에서 계산한다.
그 뒤로 딱 둘 늘었다:

- `NpcState.lastGiftedOn` (I · v18) — 오늘 이미 하나 받았는지.
- `DiscoveryState.seenSceneIds` (J · v19) — 이미 본 리빙신.

둘 다 계산으로 알 길이 없어서 적어둔다. 예전 저장에는 없으니 sanitize 가
빈 값으로 채운다 — 잃는 기록은 없다. `seenSceneIds` 를 이야기 장 옆에 둔 건
뜻이 같아서고(둘 다 "한 번 보면 끝나는 걸 이미 봤는가"), **진행도는 섞지
않는다** — `storyProgress` 는 이야기 장만 센다.

G.5 의 배경 그림은 `public/assets/city/city_map_base.webp` 한 장이다
(853 × 1844, 357KB). 화면의 지도 칸은 `MAP_CANVAS` 의 비율을 그대로
쓴다 — 비율이 어긋나면 그림이 잘리고, 잘린 만큼 누르는 자리가 건물과
어긋난다. 그림이 없으면 지도는 조용히 예전 카드 목록으로
되돌아간다 — 그림 하나 때문에 도시로 가는 길이 막히지 않게.
**그림을 바꾸면 `CITY_MAP_REGIONS` 의 좌표를 다시 잰다** — `?dev=map` 으로
누르는 자리를 켜고 맞추고, `citymap.test.ts` 가 서로 먹히는지 잡아준다.
그림에는 이름표도 상태도 얼굴도 박지 않는다. 전부 코드가 위에 얹는다.

도시 사람은 **스물넷**이다 (바이블 24명 전부). 처음 여섯은 G 뒤에
**캐릭터 바이블의 사람으로 갈아끼웠고**, id · 이야기 · 비밀 ·
레시피 · 던전 입구는 그대로 두고 이름 · 성격 · 대사만 바꿨다 (저장 판올림 없음).
도윤(`RIO`)만 혼자 존댓말을 쓴다 — 바이블의 말투 예시가 그렇다. 실수가 아니다.

사람 얼굴 스물넷은 `public/assets/npcs/<NPC_ID>.webp` 다 (256px 정사각형, 얼굴이
가운데). 파일 이름이 사람 이름이 아니라 **id** 인 건 초반 여섯이 둘 다르기
때문이다 (`MINA.webp` = 윤하루). 경로를 아는 곳은 `city/portraits.ts` 하나고,
화면은 전부 `NpcFace` 를 부른다 — 그림이 없는 사람은 거기서 이모지로 떨어진다.
시트에서 다시 뽑으려면 `npm run assets:npcs`.

**선물은 공략표가 아니다 (UPDATE I).** 셋뿐이다 — 콕 집은 것(LOVE) ·
결이 맞는 것(LIKE) · 나머지(NEUTRAL). **싫어함은 없다.** 잘못 고른 선물로
관계가 나빠지면 사람들은 실험을 그만두고 답을 찾으러 간다. NEUTRAL 도
충분히 괜찮은 결과다.

화면은 **답을 미리 알려주지 않는다.** I 이전에는 목록 위에 "하루 —
coffee · book · sweet 쪽을 좋아해" 라고 적고 물건마다 `💗 +10` 을 달아뒀다.
그러면 고르는 일이 아니라 읽는 일이 된다. 지금은 힌트가 없고, 건네보고
그 사람이 하는 말로 안다 (`city/gift-lines.ts`, 스물넷 × 세 단계 × 두 줄).

친밀도는 **1 · 2 · 3** 이다 (예전엔 5 · 10). 그 값에서는 좋아하는 물건
하나가 의뢰 하나(10)와 같았고, 가게에서 사서 스물넷에게 돌리는 게 제일
빠른 길이었다 — 그건 관계가 아니라 순회다. **하루에 한 사람당 하나만**
받는다 (`lastGiftedOn`, 인사와 같은 모양). 두 번째부터는 아예 막는다 —
0이 오르는 걸 알면서 물건만 사라지게 두면 그건 함정이다. 세는 UI는
만들지 않는다: 횟수도 연속도 안 보여주고, 안 준 날에 잃는 것도 없다.

취향은 저장하지 않는다. `likes`(결)와 `loves`(콕 집은 것 한둘)는 전부
`city/npcs.ts` 의 static data 고, 결과는 그때그때 계산한다. 알게 된 것을
적어두는 **취향 수첩은 만들지 않았다** — 선물 기능보다 도감이 커지면
그건 다른 업데이트다.

**사람은 늘려도 동네는 여섯 곳 그대로다.** 그래서 아침 카페 거리에 열둘이
모이기도 한다. 동네 시트에서 사람을 칩 한 줄로 접은 게 그 때문이다 —
칸으로 깔면 가게가 스크롤 아래로 밀린다. 의뢰는 한 사람당 하나만 둔다.

## 코드를 쓸 때

- 주석은 **왜 그렇게 했는지**를 적는다. 무엇을 하는지는 코드가 말한다.
  특히 한 번 밟은 지뢰는 반드시 적어둔다 — 다음 사람이 같은 걸 밟는다.
- 레시피·데이터를 UI 컴포넌트 안에 하드코딩하지 않는다.
- 말투는 짧고 생활적으로. 게임 문구(`SSR 획득!`, `전설 스킨 해금!`)를 쓰지 않는다.
